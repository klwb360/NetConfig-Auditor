# 独立金标准验收

在仓库根目录进入 `network-config-auditor`，运行：

```powershell
python -m unittest discover -s tests -p test_acceptance_metrics.py -v
python tools/benchmark_acceptance.py --out reports/acceptance.json
```

工具只读取本地配置，默认结果写到 `network-config-auditor/reports/acceptance.json`。可通过 `--out` 指定其他路径，通过 `--dataset` 指定采用同一冻结模式的数据集。退出码 0 表示满足门槛，1 表示验收未满足，2 表示数据文件、校验和或冻结模式无效。普通 CLI 审计退出码遵循原有接口，不被这个独立验收工具改变。

## 数据来源与覆盖

`benchmarks/configs/` 含 50 份按 Cisco IOS、Huawei VRP、H3C Comware 命令形式人工合成的校园网配置片段：Cisco 18、Huawei 16、H3C 16。它们没有采集自真实设备，没有验证设备型号或软件版本，也没有连接真实网络。厂商由清单显式指定，本指标不评价自动厂商识别。

`benchmarks/expected/` 中的 JSON 是独立指定的语义值和对象级预期结论。`author_fixtures.py` 保留逐场景人工写下的配置及预期值，不导入或调用解析器、规则引擎。计分器不调用这个编写脚本，也不根据实际输出回写标注。`manifest.json` 保存数据来源、冻结路径、场景和每份配置/预期文件的 SHA256；文件变动需经过独立标注复核及版本变更，不能为了消除失败修改预期或删样例。

数据中有 25 个风险规则的应报/不应报配对，共 50 例；一个重复地址例展开成两个受影响接口，故风险金标准共 26 个对象级结论。覆盖接口、VLAN、Trunk、静态路由、ACL、NAT、管理面、STP 和 OSPF 的指定场景。未知 ACL 条件、动态地址和缺少 VTY 来源限制独立标注为未知结论。整个规则目录共有 35 个 ID，本金标准不宣称每个 ID 都有独立正反验收，也不替代完整回归测试。

## 字段口径

字段准确率为：

`值和类型均正确的字段数 / 预期与实测支持字段键的并集大小`

它不采用命令识别行数。先按 `manifest.json.frozen_supported_paths` 的固定路径投影实际清单，再展开所有对象。某个接口、ACL、路由或 NAT 被误多解析时，其受支持字段也进入分母；遗漏字段与错误值均进入失败明细。不会仅遍历预期键而忽略实测额外对象。

冻结范围包括主机名、接口基础属性及显式 STP 属性、VLAN 名称、静态路由基础五字段、ACL 类型/顺序/规则条件、NAT 解析字段、地址池存在性、VTY 属性及全局 STP 属性。新增接口/路由 `complete` 属性、行号和证据、行数、厂商识别、OSPF 进程清单、地址池地址范围、情报/AI 输出不在本版字段准确率中。OSPF 有风险配对，但其进程字段准确率在报告中为 `null`，不能理解为 100%。地址池仅评价名称/存在性，不能理解为地址池内容已完整识别。

`null` 和空集合也是明确的预期语义值，例如没有给出 admin 状态不等于已开启。标量列表和 VLAN 范围列表按一个属性计分；路由、ACL 规则等对象列表按索引逐字段计分，顺序错误会被检测。这个范围在测量前冻结，不因实现新增字段或一次失败临时改变。数据包含默认/未知属性，故汇总准确率也包含这些值；应同时查阅模块分母和逐例错误，不把汇总值当复杂配置覆盖率。

厂商及模块采用微平均：先分别累加正确数和并集分母，再相除。不能平均每个文件的百分比，让只有一个字段的小文件与几十字段的文件拥有同等权重。

## 风险、未知及门槛

风险匹配键为 `(配置文件, rule_id, affected_object)`。合并发现中的每个对象分别计数，重复对象和重复发现去重。没有已知对象的结论使用 `device`。TP 为正确匹配，FP 为额外风险，FN 为漏掉的风险。`precision = TP/(TP+FP)`；`recall = TP/(TP+FN)` 独立输出。分母为零时为 `null`，不伪装成 100%。

未知项采用明确名单单列：`PARSE-INCOMPLETE`、`PARSE-NUMBER`、`MGMT-VTY-UNKNOWN`、`MGMT-VTY-SOURCE`、`ACL-UNBOUND`、`OSPF-AUTH-REVIEW`。不是所有 `needs-review` 都属于未知；静态映射、显式重复地址等仍是有配置证据的风险。未知结论的额外/缺失匹配不计入风险 precision，也不表示设备安全或存在漏洞。

`PARSE-INCOMPLETE` 的含义是至少有一条输入命令的格式或语义不在已完整支持范围；不是风险存在的证明。金标准要求指定未知命令的原文仍能在 `warnings[].text` 中找到，不能用一个泛化的“解析不完整”标签掩盖丢失的输入。其含凭据证据仍遵循脱敏规则。

硬门槛为字段准确率至少 95%、风险 precision 至少 90%。不设置或暗中修改 recall 门槛；它始终单列供验收者判断漏检。另需满足数据数量、厂商数量、至少 20 个风险正反配对、所有不应报断言及指定未知原文检查。指标失败时退出非零，工具不会降阈值、删失败例或生成迎合实测的预期。

## 报告接口与复核

报告主要字段是 `fields`、`findings`、`unknown`、`by_vendor`、`by_module`、`coverage` 和 `cases`。每个厂商/模块含字段微平均、风险 TP/FP/FN 与 precision/recall、未知匹配统计。`cases[].fields.mismatches` 给出路径/预期/实际；`false_positives` / `false_negatives` 给出完整三元组；`warnings` 保留定位信息。`passed` 是上述验收门槛结果，不能解释成完整安全证明。

首次 50 例实测为字段 1870/1870、风险 TP26/FP0/FN0，precision/recall 均 100%。并行添加保守静态路由解析检查后，`h3c-16-ospf-broad-control` 中的 `description Lab-route` 出现额外 `PARSE-INCOMPLETE` 提示，未知统计为匹配 8、额外 1、缺失 0；原文未丢失，未调整金标准迎合该提示。以本地重新生成的报告为当前结果，不把这次有限合成数据的高指标推广到全部生产配置。

独立复核随后发现 H3C NAT 控制例的撤销命令错误地包含正向 `inside` 参数。v1.1 按 [H3C 官方普通 NAT 服务器语法](https://www.h3c.com/en/d_202511/2698500_294551_0.htm)改为合法外侧选择器，保留空映射的人工预期和不应报断言，并重新冻结哈希。修复前实测风险 FP1、不应报断言失败，退出 1；这次数据修正以官方语法为依据，不根据实测输出改写预期。[金标准变更记录](../network-config-auditor/benchmarks/CHANGELOG.md)包含旧哈希、RED 证据及 Huawei 不同命令视图的核对结果。

实现修复后，同一 v1.1 冻结数据复测字段 1870/1870、风险 TP26/FP0/FN0，precision/recall100%，退出 0。未知统计保留上述额外提示，门槛、样例及期望语义没有放宽。

自动检查已覆盖计分公式与本地解析/规则结果。真实设备导出语法、跨版本命令接受性、实际 VLAN/邻居/转发表、流量通过、配置变更和回退均未运行，属于设备或人工验收范围。
